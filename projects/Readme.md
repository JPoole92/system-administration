# System Administration Projects

## Overview

This directory contains my hands-on **System Administration projects** designed to demonstrate practical experience administering, configuring, maintaining, and troubleshooting Windows and Linux infrastructure.

The purpose of these projects is to move beyond theoretical knowledge and demonstrate my ability to apply System Administration concepts in realistic lab environments.

Each project simulates tasks and responsibilities that may be encountered by a **Junior Systems Administrator, Systems Administrator, Windows Server Administrator, or Cloud Systems Administrator**.

Projects include implementation, configuration, testing, troubleshooting, verification, and documentation of the technologies being practiced.

---

The primary goals of this project portfolio are to:

# Project Documentation Standard

Each project is documented as a professional technical project report.

Documentation may be provided as:

- Microsoft Word (`.docx`)
- PDF (`.pdf`)
- Supporting screenshots where appropriate

Word documents are used as editable project documentation during implementation.

Completed projects may also be exported to PDF to provide a finalized portfolio version.

---

## Standard Project Structure

Each project generally contains the following sections:

### 1. Project Overview

Explains what the project is designed to accomplish.

### 2. Business Scenario

Provides a realistic organizational reason for performing the project.

### 3. Project Objectives

Defines the technical goals that must be completed.

### 4. Skills Demonstrated

Identifies the System Administration skills practiced during the project.

### 5. Lab Environment

Documents the servers, clients, operating systems, virtualization platforms, networking, and other technologies used.

### 6. Key Concepts

Explains important technical concepts related to the project and why they matter to System Administrators.

### 7. Implementation

Documents the actual configuration process.

Major implementation steps include:

**What I Did**

A description of the configuration or administrative task performed.

**Why I Did It**

An explanation of why the configuration is required or useful in a real environment.

**Verification**

Evidence showing that the configuration works as expected.

**Screenshot Evidence**

Screenshots are included where appropriate to demonstrate successful implementation.

### 8. Verification & Testing

Configurations are tested to ensure that the environment operates correctly.

### 9. Troubleshooting / Break-Fix

Projects may include intentional or naturally occurring problems that require troubleshooting.

Troubleshooting documentation follows:

**Problem → Symptoms → Investigation → Root Cause → Resolution → Verification**

This section demonstrates the ability to diagnose problems rather than simply follow installation instructions.

### 10. Project Outcome

Summarizes the final working environment.

### 11. Key Learnings

Documents the technical knowledge gained from completing the project.

### 12. Interview Knowledge

Important concepts from the project are converted into questions that could be encountered during a technical interview.

# Screenshot Philosophy

Screenshots are used as **technical evidence**, not simply decoration.

Screenshots may demonstrate:

- Successful server configuration
- Active Directory configuration
- Network configuration
- User and group administration
- Successful domain authentication
- PowerShell command results
- DNS resolution
- Service status
- Permissions
- Troubleshooting results
- Successful verification tests

Each important screenshot should answer:

> **What does this screenshot prove that I successfully configured, administered, tested, or troubleshot?**

Sensitive information, passwords, credentials, private IP information where necessary, product keys, and other confidential information should not be exposed.

# Learning Approach

These projects follow a practical learning model:

**Learn → Implement → Verify → Break/Fix → Explain → Document**

The objective is not simply to memorize configuration steps.

For each technology, I aim to understand:

- **What is it?**
- **What problem does it solve?**
- **Why would an organization use it?**
- **How do I configure it?**
- **How do I verify that it works?**
- **What commonly goes wrong?**
- **How would I troubleshoot it?**
- **How would I explain it during a technical interview?**
